# Playwright による動作確認

## 依頼に応じて計画または実行まで進める

変更が画面や操作、ブラウザ上の挙動、Cloudflare Workers 環境に与える影響を基準に判断する。確認が必要な場合は実行まで進める。計画だけを求められた場合は、手順3で計画を報告して終了する。

実行前に、確認の要否を判断した理由、確認範囲、画面サイズ、確認項目を示す。報告内容は「依頼と実施状況に合う内容を報告する」の表で確認する。

## 1. 変更内容と影響範囲を確認する

`git diff`、変更ファイル、関連実装とテストを確認し、次を整理する。ファイル名だけで影響を判断しない。

- 変更した機能と、表示・操作・ブラウザ API 連携への影響
- 共通コンポーネント、レイアウト、フック、ストア、設定、ライブラリを介して今回の変更の影響を受ける既存機能
- 単体テストが直接検証している振る舞いと、ブラウザ上で機能を組み合わせたときに、まだ確認していない挙動

影響が断定できない場合は呼び出し元や利用箇所を調べる。必要な仕様が不明な場合は依頼者へ確認し、期待結果を推測しない。

## 2. 確認の要否と画面サイズを決める

Cloudflare Workers 環境でのビルド・実行に影響する変更は、PR 作成後に Preview URL を使った Playwright の動作確認を必須とする。Wrangler・OpenNext の設定や Workers 上のサーバー処理などが対象となる。ローカルで確認済みでも、この確認は省略しない。PR 作成前は確認を計画し、作成後に実行する。

Workers 環境でのビルド・実行に影響する場合は、次の表で「不要」に当てはまっても確認する。表示にも影響する場合は PC とスマートフォンの両方を確認し、それ以外は PC で確認する。

次の表を上から順に適用する。ライブラリや共通基盤の変更も、手順1で調べた影響に応じて分類する。

| 変更の影響 | Playwright | 画面サイズ |
|---|---|---|
| 表示に影響するか、影響する可能性がある | 必須 | PC・スマートフォン |
| 表示は変わらないが、画面操作やブラウザ上の機能が変わる | 必須 | PC |
| ブラウザ上の挙動に影響しない | 不要 | — |
| 調査後も影響やリスクの有無を判断できない | 必須 | 表示への影響を否定できなければ PC・スマートフォン、それ以外は PC |

表示への影響には、コンポーネント構造、スタイル、余白、サイズ、文言、アイコン、表示条件、画面幅に応じた表示の変化を含める。画面操作や機能には、入力、ボタン操作、状態遷移、ナビゲーション、ブラウザ API 連携を含める。

表示や操作に変更があれば、単体テストが成功していても必須とする。純粋ロジック、サーバー内部の処理、開発設定、文書、単体テストだけを変更した場合は、ブラウザ上の挙動と Cloudflare Workers 環境でのビルド・実行のどちらにも影響しなければ確認は不要となる。

UI ライブラリや CSS 基盤の変更は PC・スマートフォンの両方を確認する。画面サイズに指定がなければ PC は `1440x900`、スマートフォンは `390x844` とする。不要と判断した場合は、理由を報告して終了する。

## 3. 対象画面と主要操作を計画する

影響が限定される場合は、その機能・画面・操作を対象とする。共通部品から影響を受ける既存機能も加える。ライブラリ更新、共通レイアウト、全体設定などでプロジェクト全体へ影響する場合は、全ページと主要操作を対象にする。

全ページの確認が現実的でない場合は、未確認となる範囲とリスクを示して依頼者へ確認する。独断で一部のページだけに絞らない。

プロジェクト全体を確認する場合は、次の順序で計画を作る。

1. `rg --files app` で `page.tsx`、`not-found.tsx`、`error.tsx`、`global-error.tsx` を一覧にする。
2. 各ページとその近くにあるテスト、ページが直接参照する画面コンポーネントを読む。`page.tsx` ごとに、確認対象かどうかとその理由を一行で記載する。対象ページの行には主要操作も含める。
3. 詳細が判別できないページだけ追加で実装を読む。対象ページごとに主要操作を一つ以上記載できたら、計画の調査を終える。全入力パターンや具体的な期待値までは調べない。
4. `not-found.tsx` と障害時 UI の `error.tsx`、`global-error.tsx` は通常ページと分けて記載する。

認証情報、外部 API の利用条件、安全な再現方法が不明な操作は、必要な情報と未確認の範囲を記録する。必要な情報がそろっている対象は、計画を進める。計画だけの依頼は、ここで報告して終了する。

## 4. 実行環境を準備して確認する

Playwright CLI または Playwright MCP が利用できるか確認する。どちらも使えない場合は、インストールやサーバー起動へ進まず、未実施の理由を報告して終了する。

利用できる場合は一方を選ぶ。併用は確認に必要な場合に限る。

PR を作成すると Cloudflare Workers の Preview Build が実行される。PR 作成後は手順2に従って Preview URL が必須か判断する。必須でない変更でも、必要に応じて Preview URL を使う。Preview URL を使う場合は、対象の変更を含む Preview Build の成功と接続先 URL を確認する。ローカルサーバーの起動は不要とする。ビルド失敗などで確認できない場合は、理由と未確認事項を報告し、確認済みとして扱わない。

ローカルで確認する場合は、プロジェクトで指定された方法で、今回の確認用に新しいサーバーを起動する。サーバーが起動したことと、接続先 URL を確認する。

どちらの環境でも、新しい Playwright セッションを開始する。

各対象で入力や操作を行い、次を確認する。実行に必要な仕様や認証情報、安全な再現方法が不明な操作は、確認が取れるまで実行しない。

- 変更した機能の入力、操作、状態遷移、ナビゲーション、結果表示が仕様どおりである
- 共通部品の影響を受ける既存機能が従来どおり動作する
- 今回の変更に起因するブラウザコンソールのエラーがない

表示に影響がある場合は、PC・スマートフォンの両方で次を確認する。

- 文字切れ、要素の重なり、意図しない横スクロールがない
- 操作する要素が画面外に隠れておらず、操作できる
- 変更した表示と周辺レイアウトが仕様どおりである

問題があれば再現条件、画面サイズ、URL、期待結果と実際の結果を記録する。依頼に修正も含まれる場合は、問題を修正し、同じ項目を再確認する。確認の成否にかかわらず、今回起動したサーバーと Playwright セッションを終了する。

## 依頼と実施状況に合う内容を報告する

最初に判定（`Playwright 必須` / `Playwright 不要`）と理由を示し、該当する内容を続ける。

| 状況 | 報告内容 |
|---|---|
| 不要 | 不要とした根拠、代わりに実施した単体テストなど。未実施の検証は実施済みとしない |
| 計画のみ | 対象画面・主要操作、画面サイズ、確認項目、実行に必要な未確認情報。動作確認は未実施と明記 |
| ツールや確認環境を利用できず未実施 | 未実施の理由、予定していた対象・操作・画面サイズ・期待結果、残る未確認事項 |
| 実行した | 使用した Playwright の実行手段、URL、画面サイズ、行った操作と期待結果、実際の結果、未確認事項や問題（なければ「なし」）。表示に影響がある場合は画面サイズごとのレイアウト確認結果も記載 |

証跡は保存した場合だけパスを示す。実行できなかった操作は、理由を添えて未確認事項に記載する。
