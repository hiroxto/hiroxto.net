# コミットと PR の作成

変更を目的ごとにコミットし、リポジトリのテンプレートに沿って PR を作成する。本文の草案だけを求められた場合は、作成・公開へ進まない。

## 作業の区切りでコミットする

着手時に既存差分と依頼の対象を確認し、変更を目的ごとに分ける。タスクの最後に一括でコミットせず、それぞれの変更と検証が済んだ区切りでコミットする。

- 実装とその関連テストは同じコミットにまとめてよい。説明文書や開発規則も、変更の目的が異なる場合に分ける。
- メッセージは `fix: 入力フォームのエラー表示を修正` のように、短い Conventional Commits 形式と簡潔な日本語を使う。
- 接頭辞は `feat:`、`fix:`、`delete:`、`style:`、`docs:`、`chore:`、`test:`、`ci:` から選ぶ。削除が主目的なら `delete:` を優先する。スコープや `BREAKING CHANGE` は不要。
- `git add`、`git commit`、`git restore`、`git rebase` など、インデックスを更新する操作は直列に実行する。`git status`、`git diff`、`git log` などの参照操作は並列でよい。

## テンプレートに沿って本文を作る

対象ブランチと比較先の差分・コミットを確認し、[PR テンプレート](../../../.github/PULL_REQUEST_TEMPLATE.md) を読む。タイトルは変更内容を簡潔に表す。本文はテンプレートの見出しと確認項目を保ち、変更の概要、確認内容、関連 Issue があればそのリンクを書く。

- UI を変更した場合はスクリーンショットを添付し、画面サイズとともに「動作確認」へ配置する。必要な画面サイズと操作は [plan-playwright-verification](../plan-playwright-verification/SKILL.md) に従う。
- 箇条書きに補足を加える場合は、その項目の下にインデントした箇条書きで書く。

## 作成・更新後の本文を確認する

GitHub 上の本文を取得し、テンプレートに沿っていることを確認してから完了を報告する。

`gh pr create --attach` などで画像が本文末尾に追加された場合は、画面サイズとともに「動作確認」へ移す。本文を修正した後も GitHub から再取得し、画像の配置を確認する。
