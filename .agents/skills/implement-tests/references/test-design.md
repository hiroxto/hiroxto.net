# テストケースの選び方

対象の仕様に合う節を参照する。表や例の値は、この文書内の例示仕様にだけ適用する。実際のテストでは、対象機能の確定した仕様から入力と期待結果を選ぶ。

## 同値分割と境界値分析

入力を、同じ規則で処理されるグループに分ける。各グループの代表値を選び、数値、長さ、件数、日時などに境界があれば、その境界と直前・直後を加える。

たとえば「人数は2以上6以下の整数、型変換は行わない」という仕様では、次のように整理できる。

| 分類 | 選ぶ値の例 | 期待結果 |
| --- | --- | --- |
| 下限未満の整数 | 1 | 無効 |
| 範囲内の整数 | 2、4、6 | 有効 |
| 上限を超える整数 | 7 | 無効 |
| 範囲内の小数 | 2.5 | 無効 |
| 数字の文字列 | `"2"` | 無効 |
| 値の欠如 | `null`、`undefined` | 無効 |

この例では境界の1、2、6、7で比較演算子の誤りを、小数や文字列で整数条件と型の誤りを検出する。値の種類が違っても同じ扱いかは、仕様から判断する。

- 無効な入力は、他の条件を有効にして一つずつ変える。複数の違反を同時に入れると、検証したい条件が未実装でも別の条件で拒否され、テストが通る可能性がある。
- 日時や小数では、単位、精度、タイムゾーン、境界を含むかを先に確定する。「前後」を一律に1としない。
- 代表値を増やすときは、異なる規則や不具合を検証できるかを確認する。似た正常値の大量列挙で境界値を代替しない。

## デシジョンテーブル

複数条件が結果を決める場合は、条件の組み合わせと期待結果を表にする。たとえば「通知が有効で、宛先があるときだけ送信する」という仕様なら、次の4通りを扱う。

| 通知が有効 | 宛先がある | 期待結果 |
| --- | --- | --- |
| はい | はい | 送信する |
| はい | いいえ | 送信しない |
| いいえ | はい | 送信しない |
| いいえ | いいえ | 送信しない |

- 実現可能な組み合わせを洗い出す。条件ごとの単独確認だけで、全組み合わせを確認したと扱わない。
- 到達不能な組み合わせは、到達不能と判断した仕様の根拠を記す。同じ結果になる行をまとめる場合も、どの条件が結果に影響しないかを示す。
- 条件が多いときは、結果を左右する規則や不具合の影響に応じて絞り、確認しない組み合わせを明示する。金額や権限など、重要な組み合わせを省いたまま十分と判断しない。
- 送信しない、更新しないなど、禁止された副作用も確認する。期待結果は行ごとに確定し、本番コードと同じ条件式で求めない。

## 状態遷移テスト

状態を持つ機能は「開始状態・操作・許可／禁止・操作後の状態・外部副作用」で整理する。各状態の表示だけでなく、操作による変化を確認する。

- 許可される遷移と禁止される遷移の両方を扱う。開始状態は公開 API や利用者の操作で作り、内部フィールドへ直接書き込まない。
- 禁止された操作では、拒否の結果に加え、状態が変わらず、禁止された通知や保存が発生しないことを仕様に沿って確認する。
- 終了後の再操作や同じ操作の繰り返しを確認する。再送、キャンセル後の操作、失敗後の再試行は、それぞれ仕様がある場合に扱う。
- 単発の遷移では検出できない不具合には、複数操作の順序をケースにする。無関係な操作列を際限なく列挙しない。
- 条件表と遷移表を組み合わせるときは、条件が遷移や副作用に影響する箇所を選ぶ。禁止された副作用の確認には、その副作用が発生する他の条件を満たす代表ケースを使う。全条件と全状態の直積に広げる場合は、追加で検出したい不具合を明確にする。

## エラー推測

過去の障害、変更内容、依存先の失敗から、追加すべきケースを選ぶ。推測は候補の発見に使い、期待される挙動は仕様から決める。仕様にない再試行やロールバックを必須にしない。

| 手掛かり | 確認する候補 |
| --- | --- |
| 二重送信や再送の障害 | 処理中の連続操作、完了後の再操作、重複した外部副作用 |
| 通信失敗や一部だけ完了する処理 | エラー表示、入力や状態の保持、成功表示の時点、再試行後の結果 |
| 日付や締切の処理 | 日付の変わり目、期限の前後、仕様で扱うタイムゾーン |
| 入力の正規化 | 空文字、`null`、全角と半角など、仕様上区別される入力 |
| 権限制御 | 許可される操作と拒否される操作、拒否時に副作用がないこと |

見つけた不具合は、再現する入力・操作・期待結果を回帰テストに残す。外部への操作を抑止するテストでは、ほかの許可条件を満たし、別の理由で抑止されていないことも確認する。

## チェックリストベースドテストと確認範囲

繰り返し確認する項目を、既存の仕様、障害事例、機能の特徴から選ぶ。次はフォームを持つ機能の候補であり、全機能の必須項目ではない。

| 観点 | 主な確認方法 |
| --- | --- |
| 正常な入力と入力エラー | ロジックのユニットテスト、操作と表示のコンポーネントテスト |
| 処理中の表示と二重送信防止 | 応答を制御し、未完了の間の表示と操作を確認するコンポーネントテスト |
| 失敗時の表示、入力保持、再試行 | 依存先を失敗させ、操作後の公開状態を確認するテスト |
| 権限のない操作の拒否 | 権限を判定する層のテスト。画面で操作を隠す確認だけで済ませない |
| 成功表示と保存結果の一致 | 応答前後の表示はコンポーネントテスト、実際の保存は統合テスト |
| PCとスマートフォンの表示、一連の操作 | ブラウザでの表示・操作確認 |

該当する項目をケースへ対応付け、既存テストで十分な項目は重複して追加しない。コンポーネントテストで模擬した保存や通信と、実際の連携で確認した内容を区別する。対象外や未実施の項目は、その理由や残る確認を報告する。
