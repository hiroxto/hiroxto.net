# Implement Tests

## 基本方針

実装の詳細ではなく、観測可能な振る舞いをテストする。

テストを書く前に、利用者または呼び出し元から観測できる振る舞いを特定する。主な検証対象は次のとおり。

- 戻り値
- 公開 API、画面表示、公開アクセサなどを通して観測できる状態変化
- アプリケーション外から観測できる管理外依存への呼び出し

private メソッド、private フィールド、内部ヘルパーの呼び出し、中間変数、保存形式、仕様に含まれない呼び出し順は検証しない。それらが公開契約の一部である場合だけ例外として扱う。

## 実装手順

1. 検証する振る舞いを明確にする。
   - 入力、操作、外から観測できる期待結果を言語化する。
   - 期待仕様や公開契約が不明な場合は、推測で進めず依頼者へ確認する。
   - 例示コードを書く必要があるが具体的な値や契約が未確定の場合は、その値が仮定であることを明記し、確定前に確認すべき項目を併記する。
   - 未確定の金額、ID、ラベル名、ステータス、戻り値の構造、メール本文などは、確定済みの値として記述しない。`expectedTotal`、`expectedLabels`、`expectedStatus`、`expectedEmailPayload` など、未確定の値を示す変数名やコメントで表す。もっともらしい文字列リテラルを仮値として置かない。
   - 依頼文の中で公開契約が不足または矛盾している場合は、「確認事項」と「現時点で書けるテスト方針・雛形」を分ける。矛盾している項目は、確定するまで必須アサーションとして書かず、条件付きコメントに留める。

2. コードを書く前にテストケースを選ぶ。
   - 仕様コメント、既存テスト、過去の不具合を確認し、正常系と異常系を整理する。実装の分岐だけを仕様の根拠にしない。
   - 同じ扱いになる入力は同値分割でまとめ、代表値を選ぶ。範囲や期限があれば、境界値分析で境界とその前後を確認する。
   - 複数条件で結果が変わるならデシジョンテーブル、操作履歴で結果が変わるなら状態遷移表を作る。
   - 過去の障害や失敗の起こり方からケースを補うエラー推測と、繰り返し確認する項目を使うチェックリストベースドテストを併用する。
   - 該当する技法の手順は [references/test-design.md](references/test-design.md) を読む。単純な変更に全技法や大きな表を一律に要求しない。
   - 選んだケースは「仕様の根拠・入力または開始状態・操作・期待結果」で短く整理してから実装する。未確定の項目は確認事項へ分け、同じ振る舞いの重複ケースはまとめる。

3. 検証対象とテストの種類を選ぶ。
   - 結果として表れる振る舞いは戻り値で検証する。
   - 状態変化として表れる振る舞いは公開状態、画面表示、公開アクセサで検証する。
   - 外部副作用として表れる振る舞いは、管理外依存に限って呼び出しを検証する。
   - ロジックはユニットテスト、操作と表示はコンポーネントテストで扱う。実際の保存や通信先との連携は統合テスト、画面サイズによる表示や一連の操作はブラウザで確認する。必要な確認を、単体のモック呼び出しだけで済ませない。

4. 期待値を本番コードから独立させる。
   - 期待値は、手計算、ドメイン担当者の確認、承認済みの仕様例、既存実装の確定済み出力など、テスト対象とは別の方法で求める。
   - 期待値だけでなく、入力の単位、形式、境界も公開契約に基づいて固定する。いずれかが不明なら推測せず確認する。
   - 確定した期待値は、テスト内にリテラルとしてハードコードする。複数ケースでも各ケースの期待結果を列挙する。
   - 本番コードと同じ式や分岐をテストへ再実装して期待値を計算しない。
   - 検証対象の関数、フォーマッター、定数を使って期待値を組み立てない。たとえばメッセージ形式を検証するときは、同じフォーマッターを呼ばず、期待する文字列を直接記述する。
   - 本番コードとの共有を一律に禁じない。列挙値やステータスコードなど、共有対象自体が検証対象ではなく、二重管理を避ける必要がある定数は再利用してよい。

5. 仕様に合わせてアサーションの厳密さを決める。
   - 順序に意味がないなら順序を仮定しない。
   - 一部だけが仕様なら完全一致を要求しない。
   - 必須の振る舞いが欠けても通るほど緩めない。

6. モックは必要最小限にする。
   - 戻り値、公開状態、画面表示、実データに近い値で検証できるならモックを避ける。
   - メール、決済 API、メッセージバス、Webhook、分析イベントなど管理外依存の副作用はモックまたはフェイクで検証してよい。
   - 自前 DB、内部リポジトリ、キャッシュなど管理下依存のメソッド呼び出しをユニットテストで検証しない。

7. 仕上げに独立性と壊れやすさを確認する。
   - 選んだケースとテストを照合し、境界、条件の組み合わせ、禁止された遷移、失敗時の期待結果が抜けていないかを確認する。
   - 本番コードに同じ誤りを入れたとき、期待値も同じように変わってテストが通り続けないかを考える。
   - 期待値を作るために import している本番コードが、検証対象そのものではないかを確認する。
   - 本番コードを無害にリファクタリングしただけでテストが壊れるかを考える。
   - 壊れる可能性が高い場合は、公開された結果または安定した契約を検証するように変更する。

8. テストを実行し、確認範囲を報告する。
   - 非同期の操作とアサーションは完了まで待つ。固定時間の待機で成功を判定しない。
   - 各テストで状態を用意し、モック、時刻、タイマー、保存データが他のケースへ残らないようにする。
   - 対象のテストとリポジトリで指定された確認を実行する。失敗は原因を確認し、仕様に根拠がないまま期待値を実装へ合わせない。
   - 実行した内容と結果、未実行の確認や未確定の仕様を分けて報告する。雛形だけを作った場合は、実行済みとは記載しない。

## 期待値の独立性

期待値を本番コードと同じロジックで求めると、本番コードと同じ誤りを含み、不具合を検出できないテストになる。計算結果、変換結果、外部へ送るデータなど、検証対象の出力は独立した既知の値と比較する。

非推奨:

```ts
const expected = Math.ceil(weightGrams / 1000) * 50 + distanceKm * 10;
expect(shippingFee(weightGrams, distanceKm)).toBe(expected);
```

推奨:

```ts
expect(shippingFee(2300, 4)).toBe(190);
```

ハードコード自体が根拠になるわけではない。値を確定できる仕様や別の算出手段がない場合は、もっともらしい値を置かず、依頼者へ期待結果を確認する。

## 過剰仕様のチェック

次のパターンは過剰仕様の可能性が高い。

- private メソッドや内部メソッドの呼び出しをスパイで記録し、検証している。
- private フィールドを見るためだけに `any` へ型アサーションしている。
- 内部ヘルパーが呼ばれたことを検証している。
- 仕様に含まれない呼び出し順を検証している。
- アプリが所有する DB やリポジトリのメソッド呼び出しをユニットテストで検証している。
- 順序に意味がない配列で厳密な順序を期待している。
- 重要なのが一部だけの文言に対して完全一致を期待している。
- 期待値を本番コードと同じ計算式や分岐で導出している。
- アサーションの期待値を、検証対象の本番関数やフォーマッターで組み立てている。

次の方法で検証する。

- 公開メソッドの戻り値を検証する。
- 画面表示、公開アクセサ、公開 API の結果を検証する。
- 永続化そのものが仕様なら、統合テストで実際のデータベース、または検証に必要な性質を再現した代替実装を使って確認する。
- 管理外依存への外部副作用はモックまたはフェイクで検証する。

## 依存境界の判断

プロセス外依存への呼び出しを検証する前に、管理下依存か管理外依存かを分類する。

管理下依存は、このアプリケーションが管理し、外部利用者や他システムから直接観測されない依存。例: 自前 DB、内部リポジトリ、キャッシュ。ユニットテストでは「そのメソッドが呼ばれたこと」を検証せず、公開結果で検証する。永続化の正しさが重要な場合は統合テストで扱う。

管理外依存は、外部利用者や他システムから観測できる依存。例: SMTP やメール送信、決済 API、メッセージバス、Webhook、分析イベント、通知送信。これらへの呼び出しは振る舞いの一部になり得るため、副作用が契約である場合はモックまたはフェイクで検証してよい。

## アサーションの厳密さ

仕様に合わせて、値・順序・構造をどこまで厳密に比較するかを決める。

- 順序が仕様なら正確な順序を検証する。
- 順序が不要でも、各要素の個数が仕様で決まっているなら、ソートした配列の比較など、重複を検出できる方法を使う。
- 要素の種類だけが仕様で定められ、重複の有無を問わない場合は、集合として比較してよい。
- 必須要素が含まれていればよく、余分な要素が許されるなら `arrayContaining` などの部分一致を使う。
- 文言の一部だけが重要なら `toContain` などの部分一致を使う。
- データ構造全体が仕様で定められているなら、すべての要素やプロパティを検証する。

過剰仕様と過小仕様の両方を避ける。必須の振る舞いが変わったら失敗し、実装方法だけが変わったなら通り続けるテストにする。

## private メソッド内の処理の扱い

テストのためだけに private メソッドを公開しない。

private メソッド内の処理を直接テストしたくなる場合は、その処理が単独で意味を持つ業務ルールかを判断する。該当する場合は、公開された関数、クラス、モジュールへ切り出し、その公開契約をテストする。該当しない場合は、元の公開された振る舞いを通して検証する。

## テスト名

テスト名は、内部手順ではなく「前提条件と期待される振る舞い」が分かる形にする。

推奨:

```ts
it("商品を追加すると税込み合計に反映される", () => {
  // ...
});
```

非推奨:

```ts
it("calcSubtotal が呼ばれる", () => {
  // ...
});
```
