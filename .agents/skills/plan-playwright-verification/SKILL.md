# Plan Playwright Verification

## 基本方針

変更内容が画面、操作、ブラウザ上の挙動に与える影響を基準に、Playwright による動作確認が必要かを判断する。必要と判断した場合は動作確認まで実施する。依頼者が計画だけを求めている場合は、計画の提示までとする。

判断理由、確認範囲、画面サイズ、確認観点を先に明示する。Playwright を省略する場合も、省略理由を明示する。

## 手順

### 1. 変更内容と影響範囲を確認する

`git diff`、変更ファイル、関連する既存実装とテストを確認し、ファイル名だけでなく実際の挙動への影響から次を特定する。

- 変更した機能と利用者から見える挙動
- レイアウト、スタイル、文言、表示条件、レスポンシブ挙動への影響
- 変更箇所と同じ共通コンポーネント、レイアウト、フック、ストア、設定を使う既存機能
- ライブラリの更新や共通基盤の変更によるプロジェクト全体への影響
- 単体テストで確認済みの入力・出力や振る舞いと、ブラウザで確認する必要がある挙動

影響が断定できない場合は関連する呼び出し元や利用箇所を調べる。必要な仕様が不明な場合は、期待結果を推測せず依頼者へ確認する。

### 2. Playwright による動作確認の要否と画面サイズを決める

複数の条件に該当する場合は、確認範囲が広い条件を採用する。

| 変更種別 | Playwright | 画面サイズ |
|---|---|---|
| UI の変更がある | 必須 | PC、スマートフォン |
| UI を変えないが、画面操作やブラウザ上の機能を変更する | 必須 | PC |
| UI 非依存の純粋ロジック、サーバー内部、開発設定、文書だけを変更し、ブラウザ上の挙動へ影響しない | 不要 | — |
| 単体テストコードだけを変更する | 不要 | — |
| 変更後の仕様を単体テストで十分に検証でき、ブラウザでの機能連携・操作・表示に未確認のリスクがない | 不要 | — |

UI の変更には、コンポーネント構造、スタイル、余白、サイズ、文言、アイコン、表示・非表示、レスポンシブ挙動の変更を含める。画面操作やブラウザ上の機能の変更には、入力、ボタン操作、状態遷移、ナビゲーション、ブラウザ API 連携など、見た目の変更を主目的としない、利用者が操作する機能の変更を含める。

単体テストが存在するという理由だけで Playwright を省略しない。変更した入力・出力や振る舞いを単体テストが直接検証し、かつブラウザ上で組み合わせたときにだけ生じるリスクがない場合に限って「単体テストで十分」と判断する。判断に迷う場合は Playwright を実施する。

ライブラリの更新や共通基盤の変更は、影響先を調べてから分類する。フロントエンドの描画や操作へ影響する可能性がある場合は Playwright を実施し、UI ライブラリや CSS 基盤への変更は PC とスマートフォンの両方を確認する。

### 3. 確認範囲を決める

- 新規実装や変更の影響が限定される場合は、その機能、画面、操作を確認範囲とする。
- 変更した共通部品の影響が予想される既存機能がある場合は、その既存機能も確認範囲へ加える。
- ライブラリ更新、共通レイアウト、全体設定などプロジェクト全体へ影響する場合は、プロジェクト全体を確認範囲とする。対象となる利用者向けの全ページと主要操作を列挙し、変更の影響を受ける画面を漏れなく確認する。

プロジェクト全体が確認対象の場合は、根拠なく一部のページだけを確認して済ませない。全ページの確認が現実的でない場合は、勝手に範囲を狭めず、未確認範囲とリスクを示して依頼者へ確認する。

プロジェクト全体の確認計画を作る場合は、次の手順で対象ページと主要操作を整理する。

1. `rg --files app` を使い、`page.tsx`、`not-found.tsx`、`error.tsx`、`global-error.tsx` をまとめて一覧にする。
2. 各 `page.tsx` とその近くにあるテスト、直接参照する画面コンポーネントから、利用者が行う主要操作をページごとに一行で整理する。
3. 詳細が判別できないページだけ追加で実装を読む。計画段階では、全入力パターンや具体的な期待値まで一つずつ調査しない。
4. `error.tsx` と `global-error.tsx` は通常ページではなく、再現可能な共通の障害時 UI として別枠にする。

すべての `page.tsx` について、確認対象かどうかとその理由を一覧に記載する。対象ページごとに主要操作を一つ以上記載したら、計画段階の調査を終える。認証情報、外部 API の利用条件、安全な再現方法が不明な操作は、実行方法を推測せず、確認に必要な情報として記録する。

### 4. 実行環境を準備する

1. Playwright CLI または Playwright MCP が利用可能か確認する。
2. どちらも利用できない場合はインストールを勝手に行わず、動作確認を実施できない理由として報告する。
3. `npm run dev` でローカルサーバーを新しく起動し、接続先 URL と起動成功を確認する。
4. Playwright CLI または Playwright MCP の一方を選んで確認する。確認に必要な場合だけ併用する。
5. プロジェクトで画面サイズの指定があれば従う。指定がなければ PC は `1440x900`、スマートフォンは `390x844` を使用する。
6. 確認完了後、今回起動したローカルサーバーと Playwright セッションを終了する。

既存の別作業用サーバーや Playwright セッションを使い回さない。スクリーンショットや操作結果を保存する場合は `.playwright-cli/` 配下へ置く。

### 5. 動作確認を実施する

各対象について、変更した機能が動作する条件に合わせて入力や操作を行い、画面表示や動作結果を確認する。

機能については次を確認する。

- 追加・修正した機能が仕様どおりに動作すること
- 入力、操作、状態遷移、ナビゲーション、結果表示が期待どおりであること
- 変更した共通部品による影響が予想される既存機能が、従来どおり動作すること
- ブラウザコンソールに今回の変更に起因するエラーがないこと

UI に変更がある場合は、PC とスマートフォンの両方で次を確認する。

- 文字切れがないこと
- 要素の重なりがないこと
- 意図しない横スクロールがないこと
- 操作対象が画面外へ隠れたり、操作不能になったりしていないこと
- 変更した表示と、その周辺レイアウトが仕様どおりであること

問題を見つけた場合は、再現条件、画面サイズ、対象 URL、実際の結果、期待結果を記録する。依頼が修正まで含む場合だけ修正し、修正後は同じ観点で再確認する。

### 6. 結果を報告する

次の形式で簡潔に報告する。

- 判定: `Playwright 必須` または `Playwright 不要`
- 理由: 変更種別とブラウザ上のリスク
- 確認範囲: 対象機能、画面、既存機能
- 環境: 使用した Playwright、URL、画面サイズ
- 実施内容と結果: 操作、期待結果、実際の結果
- UI 観点: PC・スマートフォンごとのレイアウト確認結果。UI 変更がない場合は省略する
- 未確認事項または問題: なければ「なし」
- 証跡: 保存したスクリーンショットなどがある場合だけパスを示す

Playwright 不要と判断した場合は、確認範囲以降の項目は記載せず、不要と判断した根拠と代わりに実施した単体テストなどを報告する。
